could not have anticipated: it depends on this machine's own development state.

## What changed from the plan's text, and why

`test_the_registry_reads_back_what_link_wrote`, as given, called `modules._write_link(...)`
*before* `monkeypatch.setenv("SUSHISTACK_HOME", str(tmp_path))`. `_write_link` opens with
`registry = dict(registered_modules())` — it merges onto whatever is already registered, so a
relink does not silently drop other modules. `registered_modules()` calls `workspace_root()`
directly; it is not covered by the `cfg_dir` fixture's `modules.config_dir` patch. With
`SUSHISTACK_HOME` still at its conftest-pinned value (the repository root) at write time, that
call reads *this developer's own* `sushihub/cli/modules.local.toml` — which already links
`sushiai`, `sushiblas`, `sushidsp`, `sushiengine` and `sushiruntime` to sibling checkouts under
`D:/Projects/`. The write merged those four unrelated entries into the throwaway registry, so
`registered_modules() == {"sushiai": str(checkout)}` failed with four extra keys.

Fix: move the `monkeypatch.setenv("SUSHISTACK_HOME", ...)` call before `_write_link`, so the
merge-on-write reads the empty throwaway workspace instead of the real one. `_write_link`'s
merge depends on `SUSHISTACK_HOME`, not on `config_dir()`; wave 3 should know that a caller
patching only `config_dir` still talks to whatever workspace the environment currently names.
Documented this in the test's own docstring rather than leaving it implicit.

A second correction in the same test: `_write_link` normalizes backslashes to forward slashes
before writing (`str(registry[key]).replace(chr(92), "/")`), so on Windows the path read back
never matches `str(checkout)` verbatim. Changed the expected value to
`str(checkout).replace("\\", "/")`.

No other assertion in the plan's text needed a change — the refusal messages, the alias
resolution, the dry-run behaviour and the sorted-entries behaviour all matched the real code
exactly as written.
