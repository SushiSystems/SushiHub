## Step 1: Declare the dependency

Added `"sushicore>=0.1.0",` to `dependencies` in `sushihub/cli/pyproject.toml`, directly above
`"typer>=0.12",`, and deleted the six-line comment block below `[project.optional-dependencies]`
that explained why the dependency was absent. Done exactly as drafted.

## Step 2: Delete the injection in `modules.py`, with one correction

Deleted the injection path from `_install_module_cli`: the `cli_shared = sushicore_dir(root)`
block through the `return False` that closed it, replaced with `return True` right after the
`pipx install` check. Updated the function's docstring; it now says it pipx-installs the
module's CLI and nothing else.

**Trap 1 (`root` parameter), as asked:** verified before touching anything. After the deletion,
nothing else in `_install_module_cli`'s body reads `root`, so I dropped the parameter. The plan
said "fix the one call site," but there are **three** call sites, not one. `add()` calls it at
lines that were 412, 424 and 449 before my edit. I fixed all three (`module_dest(root, name))`,
`dest)`, `dest)`), confirmed by `grep -n "_install_module_cli("` after the edit.

**A second problem the plan did not name, found while deleting `sushicore_dir`:**
`sushihub/cli/sushistack/services/status_report.py` (not in my file list) imports
`sushicore_dir` from `modules.py` and calls it in `_sushicore_row()` to report whether the
in-repo `sushicore/` checkout is present, for `hub status`. The plan's own text says
"`SUSHICORE_NAME` stays... `status_report.py`... still use[s] it," but that sentence only covers
the constant, not the function; it missed that `status_report.py` also depends on
`sushicore_dir`. Deleting the function wholesale, as step 2 literally instructs, breaks that
file's import, and I am not authorized to modify `status_report.py`.

**Resolution:** I restored `sushicore_dir(root)` in `modules.py`, unchanged in behaviour, with
its docstring rewritten to say it is now used for presence reporting rather than for locating
something to inject. Only its use inside `_install_module_cli` (the injection) was removed.
This is a deliberate departure from step 2's literal wording, made because the literal
instruction breaks a file outside my scope; I did not touch `status_report.py`. This should go
back to whoever owns the plan: either the plan is wrong about what still needs `sushicore_dir`,
or `status_report.py`'s `_sushicore_row` needs its own follow-up once `sushicore/` is removed in
task 6.

`_cli_package_name` (used only to compute the pipx-injected package name) became dead code once
the injection was deleted. Nothing else in the codebase calls it (confirmed by grep, one hit
left, and that was in the test I was about to rewrite). I deleted it along with the `import sys`
it was the last user of, since carrying unused code forward is a SOLID violation this task's
file list already authorizes me to fix (`modules.py` is on the list). This goes beyond step 2's
literal text; flagging it as a departure.

## Step 3: Delete the injection from the installer

In `sushihub/cli/install.py`: deleted `find_sushicore_dir()`, deleted the
`sushicore_dir = find_sushicore_dir()` line and the `if rc == 0: rc = run([*pipx, "inject", ...])`
block with its comment from `install()`, and updated the module docstring's `Strategy` section
to add a line stating `sushicore` is now an ordinary dependency resolved by the same pipx
install. Done exactly as drafted; `PACKAGE_NAME` stays, since `uninstall()` still uses it.

## Step 4: Rewrite the tests

Deleted `test_a_missing_sushicore_stops_after_the_install` (it tested a code path that no longer
exists). Replaced `test_the_happy_path_installs_then_injects` with
`test_the_happy_path_installs_the_module_cli_alone` and added
`test_a_failed_pipx_install_is_reported`, both verbatim from the plan, adjusted only to drop the
now-removed `root` argument from `_install_module_cli` calls.

**Departure required by the Step 2 correction above:** because `sushicore_dir` survives in
production code (for `status_report.py`), I did **not** delete
`test_sushicore_is_found_at_a_fixed_path_under_the_root` and
`test_sushicore_is_none_when_the_checkout_is_partial` as the plan's step 4 says. Deleting them
would leave `sushicore_dir` with zero test coverage anywhere in the suite (confirmed by grep:
no other test file references `sushicore_dir`, `_sushicore_row`, or exercises it through
`build_status`). I kept both tests and the `root` fixture they need, and widened the file's
docstring from "How a module's own CLI is installed" to "How a module's own CLI is installed,
and where the in-repo sushicore checkout resolves," since the file now covers both concerns.

**Consequence for the expected test count:** because of this, the file's test count is
unchanged (6 before, 6 after: one deleted, one added), not down by three with one added as the
plan expected. The full suite reports 334 passed, not the plan's expected 332. This is a direct,
reported consequence of the `status_report.py` dependency the plan missed, not a mistake in
counting.

1. **`_install_module_cli`'s `root` parameter** had three call sites, not the one the plan

   its use in the injection path.

   (`test_sushicore_is_found_at_a_fixed_path_under_the_root`,
   `test_sushicore_is_none_when_the_checkout_is_partial`), because the function they cover
   still exists and had no other coverage. The `root` fixture was kept for the same reason.

Items 2, 4 and 5 need the plan owner's attention: either confirm keeping `sushicore_dir` for
`status_report.py` is correct (in which case the plan's Task 6 needs to account for it once
`sushicore/` is deleted), or decide `status_report.py` should lose that status row instead, which
is a file outside this task's authorization.
