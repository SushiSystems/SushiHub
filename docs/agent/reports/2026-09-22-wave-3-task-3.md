## Which importlib form

`importlib.resources.as_file`, through two context managers shaped the same:
`config.packaged_defaults()` for the file and `dependency_source.packaged_manifests()` for the
directory. Each yields a real `Path` and each docstring says the path is only valid inside the
`with` block.

`packaged_defaults` is used entirely inside its block, so it is correct under any installation
form. `packaged_manifests` is not: `manifest_sources` returns the globbed paths and
`_parse_manifest` opens them later, outside the block. That holds for an unzipped install,
which is what pip and pipx produce and where `as_file` yields the package directory itself, and
it would break for a zipimported install on 3.12 or later, where `as_file` extracts to a
temporary directory it then deletes. Making that case work means reading each fragment inside
the block and returning its text rather than its path, which changes `IDependencySource`'s shape
and is not this task's. Nothing in the repository installs zipped.

I did not trust package data on argument. The wheel was built and opened:

## The two decisions the task asked for

**`config_dir` goes; `legacy_cli_dir` takes the one caller that is left.** The name described
the directory by what it held, and after this task it holds neither the defaults nor the
manifests. Keeping it would have pointed a truthful-sounding name at a directory whose only
remaining content is the two pre-upgrade local files. Five of its six callers are gone; the
sixth is `console.py`, which hands the directory to sushicore's `LazyConsole` so a developer's
`config.local.toml` can still override the `[cli]` theme. `LazyConsole` takes a directory and
appends the two old file names itself, so reaching `workspace.toml` needs a sushicore change,
which task 2 already recorded as a later wave's. `legacy_cli_dir` says exactly that in its name
and its docstring, and it disappears with the files.

**The `.gitignore` lines stay; the `_GITIGNORE_LINES` copies go.** They look like one fact but
they are two. This repository's `.gitignore` describes a workspace that exists: both
`sushihub/cli/config.local.toml` and `sushihub/cli/modules.local.toml` are on this disk right
now, they carry eleven absolute Windows tool paths and a developer's private link registry, and
task 2's design keeps them as the undo for the upgrade. Dropping the lines would make git
report them as untracked in every upgraded checkout and invite exactly the commit the ignore
exists to prevent. They stop being ignored when they stop existing, which is the later wave the
plan's "what this wave does not do" already names.

`_GITIGNORE_LINES` in `services/modules.py` is the opposite case: it is what `hub init` appends
to a *new* workspace's `.gitignore`, and a workspace created today never writes either file. The
two lines there were instructions to ignore something that will never appear, so they are
deleted. `test_catalog.py` gains a second test asserting they are absent, beside the one that
asserts `/.sushistack/` is present.
