# Wave 3, task 2: the marker becomes a directory

**Plan:** `docs/agent/plans/2026-09-22-wave-3-workspace-directory.md`, task 2 plus task 1's step 5.
**Commit:** `4f77be9` — `feat(cli)!: keep the workspace's data in a .sushistack directory`.
**Suite:** 351 passed, up from the 341 this task started at.

## What landed

`.sushistack` is a directory holding `workspace.toml`, with `[workspace] version = "1"`,
`[modules]` and `[tool]` in one file. `sushistack.config` gained `workspace_file`,
`create_workspace_file`, `upgrade_workspace`, `CHECKOUT_CLI_DIR` and `WORKSPACE_HEADER`, and
re-exports `WORKSPACE_MARKER` and `WORKSPACE_FILE` from sushicore 0.2.0. The dependency pin in
`sushihub/cli/pyproject.toml` is `sushicore>=0.2.0`, which is task 1's step 5.

`workspace_root` no longer treats a `sushihub/cli/manifests` tree as a marker. It still accepts
the old marker file, because `upgrade_workspace` has to reach a workspace before it can convert
it. The conversion runs from `_root` in `cli.py`, behind the three guards the plan named:
`--describe` exits first, `hub` with no subcommand exits first, and an unresolved root returns
without an error so `hub init` still runs outside a workspace.

`config_dir` survives, narrowed to "the checkout directory holding the committed defaults and the
dependency manifests". Nothing the workspace owns is written there any more. Task 3 empties it and
removes the function.

## The two decisions the plan asked for

**`links.write` goes through `write_toml_document`.** Reading sushicore's `config_base.py`
settled it: `write_toml_document(target, tables, header_lines)` is the single renderer, and
`write_tool_section` is nothing but the caller that merges `[tool]` before handing the whole
document over. `links.write` now does the same for `[modules]` — read the document, merge the one
entry, re-render. There is no second whole-file writer, and the tool paths survive a `hub link`.
`test_a_link_written_after_an_upgrade_keeps_the_tool_paths` holds that.

**`hub remove` empties `[tool]` rather than unlinking the file.** Refusing would leave a developer
no way to reclaim stale tool paths, which is the only thing `hub remove` ever took from that file;
deleting the file would now cost them their links, which `hub remove` never placed there.
`_remove_config` reads the document, drops `tool`, and re-renders. Two tests cover it, one for the
write and one for the dry run.

## Two hazards the plan did not name

**A third whole-file rewriter.** `ConfigureStep` at `steps.py:775` called
`target.write_text(probe.render_local_config(...))`, which would have erased `[modules]` and
`[workspace]` on the first `hub install` after an upgrade — the same defect the plan's step 4
forbids, in a file the plan does not list. `probe.write_platform_paths` replaces it: it merges the
probed values into `[tool.<platform>]` through `write_toml_document`. `render_local_config` stays,
used only for the dry-run preview.

**`.sushistack` was tracked in git.** The old marker was an empty file committed to the
repository. `workspace.toml` holds machine-local absolute paths and a developer's own link
registry, so it must not be. The commit deletes the tracked marker and adds `/.sushistack/` to
`.gitignore` and to `_GITIGNORE_LINES` in `services/modules.py`. The plan gives `.gitignore` to
task 3; leaving it there would have meant committing this developer's tool paths in the meantime.
Task 3's other two lines are untouched.

## What did not work, and why I stopped

`hub install --dry-run` in that fresh directory fails:

```
[ERROR] No dependency manifests found. Expected at least
sushihub/cli/manifests/*.deps.toml in the SushiStack workspace.
```

The plan's step 6 expects it to run, but its own amendment defers
`setup/dependency_source.py:148` to task 3, and that line is what reads the manifests out of the
checkout. Until task 3 ships them inside the package, no directory without a `sushihub/cli/`
tree can install. I left it rather than moving the manifests early.

## Two gaps for a later wave

`console.py` still builds `LazyConsole(config_dir)`, so a `[cli]` theme override is read from the
checkout's `config.toml` and `config.local.toml`, never from `workspace.toml`. sushicore's
`LazyConsole` takes a directory and appends those two names itself; reaching the new file needs a
change in sushicore, which this task may not make. Nothing regressed — the old override still
works — but the new file is not a place to put a theme yet.

`write_toml_document` always emits a `[tool]` header, so a file with no tool paths still parses
back an empty `tool` table, and `hub remove` leaves `[tool]` empty rather than absent. Readers see
`{}` either way. The `file-formats` skill asks for an integer `format_version`; the owner's
decision fixed `[workspace] version` as a string instead, and the plan's tests assert it, so that
is what shipped.
