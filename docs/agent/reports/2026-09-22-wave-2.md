**Departure — `owner_order`'s argument (the task's first check-first item).** Read
`sushihub/cli/sushistack/setup/ordering.py:15`: `def owner_order(source: IDependencySource,
owners: Iterable[str]) -> list[str]`. The call site at `setup/steps.py` (`_report_readiness`) used
to pass `MODULES`, a `dict[str, Module]`, which under `owner_order`'s iteration yields its keys —
plain module names. `CATALOG` iterates the same way (`ModuleCatalog.__iter__` yields names), so it
satisfies `Iterable[str]` identically to what `MODULES` did. I passed `CATALOG` directly rather
than `CATALOG.names()`: same behaviour, one less list built on every readiness report. Verified
with `hub status` below, which reaches this code path.

**Departure — `cli_install.py`'s docstring.** Its module docstring named `MODULES` by name
(`"resolved from ``MODULES`` in :mod:`sushistack.services.modules`"`). That symbol no longer
exists after this task. `cli_install.py` was not in the plan's file list for any task, but a
docstring naming a deleted symbol is a defect the moment task 1 lands, so I judged it out of
scope for a write here and am flagging it instead: `sushihub/cli/sushistack/services/cli_install.py:4`
still says `MODULES`; it should say `CATALOG`. Left untouched because the write-scope constraint
for this dispatch names specific files and this one is not among them — noting it rather than
silently expanding scope.
