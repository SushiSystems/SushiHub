## What was built

`cli/sushidsp/services/setup.py` holds the command; `cli/sushidsp/cli.py` gains a Typer
`setup` that parses `--install` and delegates, like every other command in that file.

The service takes one of two paths and names it every time:

- A workspace above the checkout, with `hub` resolvable, means `hub install` owns the job.
  `sd setup` reports that and prints the command; `--install` runs it in the workspace root.
- Otherwise it reads `cli/sushistack.deps.toml` through `sushicore.deps_fragment.read` and
  reports every entry, then runs under `--install` exactly the commands it reported.

A workspace whose PATH carries no `hub` warns and falls through to the second path rather than
failing, because the fragment is still readable and the entry is still installable by hand.

The three states come straight from `sushicore.Status` and are not collapsed. `SATISFIED` says
the declared check passed. `NOT_APPLICABLE` says the entry names no package on this platform,
which is `intel-llvm`'s case. `UNKNOWN` says a package manager is the one that knows, and the
command names the apt or vcpkg line instead of claiming the package is missing. The README
states that limit in a sentence rather than leaving a reader to infer it.

Nothing about the fragment schema was reimplemented: `read`, `status`, `install_command`,
`Status` and `Dependency.packages_for` all come from `sushicore` 0.3.0, and
`cli/pyproject.toml` now pins `sushicore>=0.3.0`. The workspace lookup is
`config.workspace_home`, the same one `bundled_clang()` uses; no second walk was written.

## `sushi-module.toml`

```toml
[module]
name = "sushidsp"
alias = "sd"
distribution = "source"
repo = "https://github.com/SushiSystems/SushiDSP.git"
```

`repo` is written because the URL is a fact about the module that only the module knows, and
`hub` has no catalog entry carrying it. `fragment` is left out: the file sits at
`cli/sushistack.deps.toml`, which is the documented default, and a key every repository spells
identically is a constant six repositories would have to repeat.

## One thing the owner should know

The pipx venv for `sushidsp-cli` carried `sushicore` 0.1.0, so the first `sd check` after the
change died on `cannot import name 'deps_fragment'`. It was upgraded with
`pipx runpip sushidsp-cli install -U "sushicore>=0.3.0"`, which is what the new pin in
`cli/pyproject.toml` asks for; every command above ran after that. Any other machine with an
editable or pipx install of this CLI needs the same upgrade.
